# 数据库压缩只用 VACUUM,不引入压缩扩展

Status: Accepted

## 背景

设置页「数据库占用」需要给管理员一个"压缩数据库"的动作。SQLite 世界里"压缩"有两条完全不同的路:

1. **数据压缩(写时压缩行/页)**:官方只有 **ZIPVFS** —— 属 SEE(SQLite Encryption Extension)家族,
   收费、闭源、需要 C 编译;第三方绕法是可加载扩展(如 `sqlite-zstd`),需要 CGO 编译或运行时
   `load_extension`,并且**改写库文件的存储格式**。
2. **文件压缩(`VACUUM`)**:官方内置,按当前数据整体重写库文件,回收空闲页、去碎片。

本项目已有约束:ADR-0005 定了纯 Go 驱动 `modernc.org/sqlite` + `CGO_ENABLED=0`(Dockerfile 与
Agent 构建都是该约束),存储层不引入任何外部数据库或扩展。

## 决策

「压缩数据库」= `VACUUM`(前后各一次 `PRAGMA wal_checkpoint(TRUNCATE)`),**不引入任何压缩扩展**,
UI 与文档一律把它讲成"回收空闲页、把空间还给操作系统",不叫"数据压缩"。

理由:

1. **占用膨胀的来源就是空闲页**:库只涨不缩的唯一原因是保留期清理的按批 `DELETE FROM results`
   把行删了、页留在 freelist 里。`VACUUM` 正是针对这个问题的官方手段,不需要额外的压缩层。
2. **压缩扩展与构建约束正面冲突**:ZIPVFS/SEE 收费且需要 C 编译;`sqlite-zstd` 一类要么 CGO、
   要么 `load_extension`,两者都被 ADR-0005 排除。
3. **改写存储格式是不可接受的代价**:用 ZIPVFS 之后库文件不再能被标准 `sqlite3` 命令行打开,
   备份、救数据、排障都得带上那个扩展 —— 对一个"单文件 + 单容器"的部署形态是硬伤。
4. **收益不匹配**:结果表里可压缩的正文(错误原因等)占比未知,而 `VACUUM` 已经能把
   "删掉 99% 结果"的库从 15.5 MB 压回 151 KB。

## 关键约定

- **同步接口、管理员显式触发、不做定时任务**:`VACUUM` 持有唯一写连接的独占锁,期间轮次与
  结果写入排队;自动执行会在无人预期时拖慢写入路径。
- **只允许一次并发**:`compactMu.TryLock()` 失败即返回 `ErrCompactBusy`,接口回 409。
- **口径与「数据库占用」一致**:压缩前/后都用 `page_count × page_size`,页面数字与压缩结果能对上。
- **WAL 前后各截断一次**:前一次让 VACUUM 看到库文件的最终形态,后一次避免占用只是从主库挪到 `-wal`。
- **不承诺压缩率**:没有空闲页时压缩不释放空间,接口仍返回成功并由页面明确提示"已是紧凑状态"。

## 已知后果与退出条件

- 库里全是活数据时压不出空间;`freelist_count` 与实际可缩量不完全等价(页内碎片、索引页),页面文案用"约"兜。
- 同步请求在 GB 级库上会长时间挂着(前端按钮 loading、超时放宽到 10 分钟)。**若库涨到 GB 级,
  本决策不改,但实现必须改成后台任务 + 进度轮询。**
- **若将来确实需要写时压缩**(例如结果表的正文占比大到 `VACUUM` 也救不回来),正确的出路是
  **在应用层压缩特定字段**(如 gzip 后存 `BLOB`,写入路径唯一、可控、仍可用标准工具打开),
  或者换存储引擎(见 ADR-0005 的退出条件),而**不是**挂 ZIPVFS。
